\section{Overview, guarantees and threat model}\label{sec:overview}
\subsection{Product statement and scope boundary}
The product is an object-storage and fine-grained access-control platform. It owns the logical namespace, immutable object versions, protected metadata, document and text-unit identities, publication, disclosure and audit. A shared decision authority determines who may perform each operation on those resources. The default is deny: every route and resource needs an explicit complete allow, and every stored payload is encrypted; there is no plaintext storage mode. Each bucket has an encryption mode (decision D-12, Section~\ref{sec:custody}). In server mode, the default, the platform encrypts uploads and decrypts for a reader only after a fresh decision has released that version's data key. In client mode, which a bucket opts into, clients encrypt before upload and alone decrypt after download, so TLS termination reveals no plaintext to any server role. Storage services enforce the result at read, key release, encrypted-key-envelope delivery, write and publication boundaries. This foundation serves ordinary applications, people and workloads without requiring an AI model, agent runtime or MCP connection.

MCP is a later service that communicates with this foundation through its authenticated service API. It exposes selected storage and document operations as MCP tools and resources; it does not own the stored content or become the authorization authority. S3 is another protocol adapter. An AI proxy or external tool executor is an optional application of the platform, built after the storage foundation and baseline MCP service are qualified.

``Access for everything'' means one resource/action vocabulary and a shared enforcement contract wherever the platform mediates access. It does not mean control over arbitrary operating-system calls, third-party credentials, databases or files outside those paths. Fine granularity includes a bucket, object, immutable version, protected metadata, document or individual text unit. A resource is protected only when every relevant route is mediated or independently restricted.

\textbf{Implementation direction.} Coding has started in \path{/Volumes/workdata/new_idea}. This revision clarifies design contracts and qualification only; it does not assess, modify or claim conformance for that implementation. Existing work is to be evaluated against these boundaries before further feature work: complete storage and access control first, then implement MCP as their client. The project is a separate storage product; an AI-firewall deployment is one later use case.

\reqn{OVR-001}{P0}{REV}{Every release publishes an enforcement coverage matrix that lists each access route to protected resources (adapter, operation, resource type, action, mediation point, verifying test). A route that is absent from the matrix \mustnot\ be described as protected.}
\reqn{OVR-002}{P0}{LINT}{Each threat in Table~\ref{tab:threats} maps to at least one requirement and one test, and each guarantee in Table~\ref{tab:guarantees} maps to at least one requirement and one test. The specification check fails when a mapping is missing or names an undefined identifier.}
\reqn{OVR-003}{P0}{REV}{Product documentation and external claims \mustnot\ state more than the guarantees in Table~\ref{tab:guarantees} and \must\ repeat the non-guarantees in Table~\ref{tab:nonguarantees} wherever revocation, model-output control, encryption or storage durability is described.}

\textbf{Out of scope for this specification:} attribute-based and proxy re-encryption, erasure-coded storage, compiling policy into database queries, general file-content redaction, FTP/SFTP, S3 Select, tiering, site replication, and mediation of unrestricted local shells or direct local file reads.

\subsection{Releases and exit gates}\label{sec:releases}
Delivery follows the dependency order: encrypted durable storage plus access control, decision-bound key release and recipient-envelope delivery; MCP access to that storage; optional model and external-tool services. R1 is a usable storage product, not a policy-only prototype. The blob backend (our own single-node store in R1) holds private immutable ciphertext; the platform still owns the namespace, permissions, version lifecycle, document structure and user-facing API. The server retains only the declared policy/routing metadata in readable form; content remains encrypted at rest in both modes, and in client mode sensitive descriptive fields are client-encrypted too. A release is accepted only when its applicable exit tests (Section~\ref{sec:testmatrix}) pass.

Phase P0 labels process requirements that apply from the first commit. Payload encryption in both modes, per-version data keys, decision-bound server key release and, for client mode, client-only decryption and recipient-bound encrypted-envelope delivery are R1-B prerequisites. Independently encrypted document units are R1-C. Backend, catalog, audit and backup encryption at rest is additional defence, not a substitute for payload encryption. No plaintext storage profile is offered. S3 compatibility and a custom replication engine are deferred engineering work, not prerequisites for being an object-storage product; R1 backup and restore qualification remain mandatory, and multi-node redundancy is qualified only when that topology is deployed. Everything runs locally for now (D-02): the R1 profile is one node with our own single-node blob store.

R1-A, R1-B and R1-C are subphases of one release: none is deployed to production alone (\rr{GATE-003}). MCP implementation follows acceptance of that encrypted storage foundation. Baseline MCP retrieval needs a compatible decrypting client only for client-mode content, and no model provider, general tool executor or downstream connector. Optional surfaces remain disabled until their requirements and cases pass. Shared tests contribute cases with explicit phase and feature applicability. Structural checks validate those declarations; release qualification also requires applicable concrete fixtures and recorded execution evidence. This is one evolving evidence corpus, not a duplicate suite per release or adapter.

\textbf{Security priority.} Security and correctness take precedence over implementation speed, convenience and line count. Missing authority fails closed; every enabled alternate route obeys the same resource checks; no role receives credentials beyond its boundary; and recovery is proven against the declared failures. Small code and tests mean fewer mechanisms and fewer duplicates, never omitted validation, cryptographic binding or recovery evidence. No implementation is called secure merely because this specification compiles.

\subsection{Threat model}\label{sec:threats}
\textbf{Assets.} A1 encrypted content, plaintext held by authorized clients and, for server-mode content, plaintext held transiently by the storage role; A2 client private keys and data keys, opaque recipient envelopes, server-mode KEKs and wrapped data keys, and separate server signing keys; A3 policy bundles, identity, delegation and other authority state; A4 approvals, budgets and invocation state; A5 audit evidence; A6 credentials for downstream tools.

\textbf{Adversaries.} E1 malicious or curious tenant user; E2 manipulated agent or model (prompt injection, hostile retrieved content); E3 compromised or malicious tool server, connector or downstream service; E4 compromised gateway, content-service or encrypted-envelope process; E5 reader of storage disks or backups; E6 compromised client or organization key custodian; E7 over-privileged or malicious administrator, including a policy author; E8 network attacker; E9 recipient that retains exported keys or plaintext. A host operator able to replace server software (E10) can defeat server enforcement and read server-mode content, but does not obtain client-held payload keys merely by doing so. Protection against compromised client software, malicious key custodians and colluding authorized recipients is not claimed (\rr{ADM-003}, N-03).

\textbf{Trust boundaries.} TB1 client and adapter; TB2 adapter and decision service; TB3 content service and encrypted-envelope service; TB4 executor, connector and downstream service; TB5 storage processes and blob backend; TB6 control plane and administrators. Section~\ref{sec:trust} lists the evidence that crosses each boundary.

\subsection{Architecture and roles}\label{sec:arch}
The storage service owns the operation and the decision service owns policy evaluation. Adapters carry authenticated identity and delegated authority across their boundary; backend credentials remain with storage. Client-mode data keys and recipient private keys remain with clients, and the envelope service stores only their recipient-encrypted key packages. Server-mode data keys are stored only wrapped under tenant KEKs that the \code{keys} role alone holds. No caller can bypass the catalog by presenting an object path or a previously allowed MCP tool name.

\subsection{Conventions}
Requirements have the form \textbf{[ID]} statement \reqtag{phase}{tests}. Each identifies a coherent behavioral contract and its verification boundary. The phase is one of P0, R1-A, R1-B, R1-C, R2, R3. The tests are identifiers from Section~\ref{sec:testmatrix}; \code{REV} means a release review item and \code{LINT} means the specification check. A superscript \textsuperscript{\color{accent}\tiny NEW} marks a requirement added or strengthened since version 1.3; Appendix~\ref{app:mapping} maps every version 1.3 requirement to its successors.

\must, \mustnot\ and \should\ carry their usual normative meaning. Limits and numbers marked ``initial'' or ``target'' are proposals to be qualified, not measured properties. Sizes use KiB = 1024 bytes. Money uses integer minor units with an explicit currency (\rr{DAT-005}).

The case catalogue and fixtures in \texttt{vectors/} are summarized in Appendix~\ref{app:vectors}. Scenario-only cases state required behavior; concrete fixtures and recorded runs supply qualification evidence (\rr{TEST-003}).

\textbf{Design latitude.} The normative boundaries, authority checks, failure outcomes and release evidence are binding. Interface sketches and module examples explain responsibilities; they do not prescribe incidental names, internal data structures or algorithms. Implementations may choose simpler or better mechanisms that preserve these contracts and demonstrate the same invariants. Byte encodings, dependency pins and operational recipes belong in the qualified companion profiles and runbooks, rather than being inferred from a sketch.

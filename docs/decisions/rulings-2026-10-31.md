# Owner rulings, 31 October 2026

The owner agreed the plan in section 6 of [the handoff](../spec/HANDOFF.md) with these rulings. They settle items that specification 2.5 leaves open ([errata](../spec/ERRATA-2.4-to-2.5.md), "Deliberately not changed") for R1 only. They do not change the specification's text (TEST-003).

| # | Item | Ruling |
|---|---|---|
| 1 | Specification in the repository | 2.5 replaces 2.2 in `docs/spec`. 2.2 stays in git history. |
| 2 | Commits | One commit per finished item, after `make check-pg` passes. |
| 3 | DEC-001 transport | JSON only in R1. Protobuf is used only where RCP-006 needs a deterministic encoding (`RecipientEnvelopeContextV1`). |
| 4 | Retention and legal hold | R1 has reference guards only (a version still referenced by a live head, an upload or an envelope cannot be removed). No time-based retention and no legal hold until a requirement defines them. |
| 5 | D-04 identity providers, D-08 client key custody | Stay open. R1 code ships a development identity profile and test keys only. No production payload is accepted (D-08 gates it). |
| 6 | Approver authority | An `approve` action on the resources themselves (storage objects and buckets, document versions and units, derived outputs). Approvers are granted by ordinary policy rules on the same resources; there is no fixed approver role. Whether an owner may delete a version, relabel or approve is decided entirely by policy. |
| 7 | Default deny | The platform works like a default-drop firewall: an action with no rule allowing it is blocked, reads and lookups included. Every user-facing operation is a registered operation decided by the policy engine. The only exceptions are the health and readiness probes (redacted aggregate state, REL-006), the local administrator's tool for bootstrap and recovery (ADM-003) and commands that run only on the client. |
| 8 | MCP identity hop (R2) | The MCP role carries the user's identity to the storage role as a signed decision per MCP tool call, the trust table's TB3 as written: the MCP role asks the decision role about the call with the user's token and presents the decision; the storage role accepts it only from the MCP role's workload, and the decision role accepts it as the user's evidence for the storage role's own checks. The user's token never leaves the MCP role. MCP tools are `agent.tool` resources in the core type set, so each call has its own check (MCP-003). The first scope is users' own MCP clients; agents acting for users through delegations come later. The core changes stay small and additive. |

Focus: object storage plus access control first (R1). MCP comes afterwards (R2). The tools and executor stack stays in the tree as the optional R2 feature `executor` and is not extended.
